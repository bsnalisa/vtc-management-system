# Architecture rules
- Keep the system visual theme in global semantic HSL tokens and shared UI primitives so every role inherits consistent presentation without changing authorization or workflows.
- DashboardLayout remains the common role-page shell with a fixed top header, collapsible sidebar and scrollable content; role colours identify roles without overriding the shared system palette.
- Load locally packaged fonts through the global stylesheet so system typography does not depend on remote font requests.
- Organization branding may customize content accent tokens, but sidebar tokens always inherit the shared workspace theme; removing branding restores stylesheet defaults.
- Keep the public training hero in a dedicated component using the shared Embla carousel and UI controls, with pause-on-interaction and reduced-motion support to preserve accessibility independently of application workflows.
- Use AppLogo and its shared favicon asset for application branding; keep uploaded organization logos separate as centre identity so tenant branding cannot replace the system mark.
- Dashboard shells render AppLogo only in the persistent header and use a persistent SidebarProvider with one shared SidebarTrigger inside the sidebar; collapsed navigation remains a scrollable icon rail at every size so staff never lose navigation access.
- All animated loading states use LoadingIndicator directly or through LoadingSpinner/ButtonSpinner so pages, permission checks and action buttons share accessible graduation-cap motion.
- Shared UI primitives own narrow-screen containment for tabs, tables and dialogs; page action rows stack before expanding to preserve readable text without hiding workflows.
- Shared tables retain intrinsic column widths and non-wrapping cells with local horizontal scrolling; descriptive cells can opt into wrapping so sidebar expansion never crushes table text.
- Trainee and class lists switch to labelled record cards based on available content width, preserving existing actions and data so expanded navigation cannot force narrow-screen horizontal scrolling.
- Attendance, timetable history, assessment and trainer-assignment read policies use authenticated centre-role membership and relevant trainee/trainer access; SECURITY DEFINER helpers avoid recursive related-table RLS checks, and write policies must not bypass read boundaries.
- DashboardLayout derives sidebar items and group label from useRoleNavigation for the signed-in role, ignoring page-supplied menus, so navigation labels stay identical across every page a role visits.
- Organization Admins are confined to their own centre and are read-only on finance and grade tables with no way to start an override (`start_admin_override` now refuses; the existing gate stays so an override row, if one ever exists, is honoured); the five finance tables the review found writable (`financial_queue`, `trainee_financial_accounts`, `billing_records`, `finance_settings`, `department_budgets`) are in that gate, and any new finance or grade table must be added to it in the access migration. Anything an admin changes in the gated tables, the trainee and application tables, the fee queue and the role, settings and ticket tables is recorded in the append-only `admin_audit_log`. An admin cannot delete trainee, application or registration records. Only super admins grant, change or remove administrator roles.
- Centre isolation: every RLS table carries a RESTRICTIVE "Centre isolation" policy (migration 20261016090000) so staff with a centre role only touch rows of their own centres, whatever older permissive policies say; tables without a centre column take it from their parent row. New tables with an organization_id column need the same policy; super admins, platform staff, applicants and service-role code are unaffected.
- SECURITY DEFINER functions and edge functions bypass row security, so they must check the centre themselves: SQL functions that take a centre or trainee id call `assert_centre_access` / `assert_trainee_access` (migration 20261017090000), edge functions use `supabase/functions/_shared/caller.ts` (`identifyCaller`, `canActOnCentre`, `hasRoleOrOverride`), platform jobs accept only the service key, `x-dispatch-secret` or platform staff, and anonymous visitors may call only the public-site and token functions. Every role except the platform team needs a centre (`user_roles_centre_required`).
- Centre Manager (`centre_manager`) is the read-only head of a centre: it reads its own centre through one `centre_manager_overview` function and per-table SELECT policies, changes nothing directly, and only a super admin grants it. Registering trainees belongs to the registration officer; Organization Admins cannot create trainee, registration or enrolment records (migration 20261018090200) and only support trainee accounts afterwards.
- Entry requirements belong to registration: registration officers propose changes and the Head of Trainee Support (whom they report to) approves them (`save_entry_requirement`, `review_requirement_change`). Organization Admins give technical support only and have no access to entry requirements or their approval.
- Applications are either submitted online by the applicant (lands in the inbox of the chosen centre's registration officers) or captured by a registration officer for someone who applied at the centre. A captured application requires an email and triggers `create-applicant-account`, which creates or links the applicant login and sets `applicant_user_id` (`created_by` stays the capturing officer); applicants see applications where they are `created_by` or `applicant_user_id`. Screening then continues identically for both.
- Applicants (and centre capture) only see trades that have an approved, active qualification, via `trades_open_for_application`; screening warns when an application's trade has none, because such an applicant could not be registered.
- Reporting hierarchy: `reporting_lines` (per centre, seeded with the default matrix by `seed_reporting_lines`) and optional `user_supervisors` overrides decide who supervises whom; workflow steps with approver `@supervisor`/`@supervisor2` route to the submitter's direct (or next-level) supervisor, falling back to the Centre Manager when there is none. Every approval request has a `WF-YYYY-NNNNNN` reference, the submitter's role and a next action; statuses are shown with the shared vocabulary in `components/workflow/status.ts`. Decisions (approve, reject with reason, return for correction with comments, escalate with comments) go through `workflow_act_as`, the submitter can never decide their own request, and `workflow_events` is append-only. New finance/administration roles (`accountant`, `head_of_finance_admin`, `creditors_officer`, `loan_officer`, `pa_to_centre_manager`) extend the existing roles; the existing Debtor, Assets and Maintenance, Assessment, RPL and Registration roles stand in for those positions.
- Finance and administration (Head of Finance and Administration, Accountant, Creditor's Officer, Debtor's Officer, Assets and Maintenance Coordinator): records are changed only through the SECURITY DEFINER functions in migration 20261024090000 (`record_supplier_invoice`, `request_invoice_payment`, `record_supplier_payment`, journal-entry, `request_debtor_adjustment`/`apply_debtor_adjustment` and `request_asset_approval` functions), each of which checks the caller's role at the record's centre; the tables (`supplier_invoices`, `journal_entries`, `debtor_adjustments`, `asset_requests`) have no write policies and finalised rows can never be edited or deleted (corrections are reversals or adjustments). Approval and execution are separate stages (the approver cannot also record the payment or apply the adjustment); requests need their supporting documents (`workflow_attachments`) before submission where the process type requires them, and amounts above a centre's `workflow_escalation_limits` go on to the approver's supervisor automatically.
- NSFAF funding administration (Loan Officer, migration 20261025090000): the VTC does not issue loans, so the Loan Officer dashboard only administers trainees' funding from the Namibia Students Financial Assistance Fund; nothing is treated as a debt owed to the VTC. `funding_*` tables are read-only with no write policies; all changes go through SECURITY DEFINER functions that check the caller's role at the record's centre (only `loan_officer` writes). Application, eligibility, award, payment and registration status are separate fields; the VTC never approves funding, an award is recorded only as an externally issued NSFAF decision (`record_nsfaf_decision`: NSFAF reference, source, date and the award letter or correspondence on file). Payments are recorded by the Loan Officer and reconciled by Finance (accountant, head of finance, debtor's officer) and never by the officer who recorded them; a reconciled payment is final. `funding_events` is the append-only audit trail with before/after values; records are never deleted. Dashboards read through `funding_cases_base` / `funding_register` (server-side filtering and pagination), which only return the caller's centres.
- Centre Manager's office (migration 20261026090000): the PA to the Centre Manager keeps the `office_correspondence`, `office_meetings` and `office_tasks` registers through `office_*` SECURITY DEFINER functions (read-only tables, never deleted, readable only by the PA and the Centre Manager at that centre). The PA has no approval authority of their own and no policy on finance, personnel, funding or trainee tables: they decide only requests the Centre Manager delegates through `workflow_delegations`, listed with the decisions taken under them by `office_delegation_log`. The Centre Manager stays read-only; `centre_manager_executive` gives the escalated approvals, per-department workload (by the submitter's role) and indicators, and is refused to every other role.
- Proof of registration: there is one template, `proofDocumentHtml` in `src/lib/proofOfRegistration.ts`, used by the preview and the print everywhere (`ProofOfRegistration` / `PrintProofButton` in `components/registration`), so no page may build its own version. Nothing centre-specific is coded into it: logo, name, address, contacts, registration clerk, signatory and colours come from the registration's own centre (`proof_of_registration_settings`, migration 20261027090000), which only that centre's Organization Admin or a super admin changes through `save_proof_settings` (audited). The document is assembled by `proof_of_registration_data` from live records (trainee, qualification unit standards, the trainee's fee ledger for the academic year) after a role and centre check, and prints and downloads are logged in the append-only `proof_of_registration_prints`.
- Global trainee identity (migrations 20261028090000/20261028090100): a person is one row in `trainee_identities`; each `trainees` row is that person's registration at one VTC and always carries the identity's permanent number in `trainees.trainee_id`, set by the `trainees_enforce_identity` trigger (never taken from the caller, never editable). New numbers are `YYYYRRRRR` (first-registration year plus five random digits from `secure_digits5`), issued only by `allocate_trainee_identity` / `identity_resolve`, with uniqueness enforced by `trainee_number_ledger` (every number ever issued, so none is reissued, including legacy aliases and merged identities). Existing numbers were kept as `legacy` and can be remapped one identity at a time by the platform team (`remap_legacy_identity`). The legacy generators (`generate_trainee_number` and friends) are retired and raise. A person has at most one active or deferred registration across all VTCs (`uq_one_active_registration` plus the trigger); possible duplicates open `identity_review_cases` and are never merged automatically (`merge_identities` is platform-only and audited in `identity_audit_events`). Moving between VTCs happens only through `trainee_transfers`: `submit_transfer_request` (the trainee, for their own active registration), `decide_transfer` (Head of Training, then a different Head of Trainee Support, never the requester) and the internal `execute_transfer`, which moves the registration in one transaction, records a FAILED state on error and is idempotent. The login and trainee role move with the active registration; the source record stays as `transferred`. Race conditions are covered by `supabase/tests/concurrency.sh`.
- Function exposure and CI (migration 20261029090000): anonymous visitors can execute only the public-site and token functions plus the helpers that anonymous row-level-security policies, column defaults or views depend on; every other `SECURITY DEFINER` function is granted to `authenticated` and `service_role` only, and new functions are closed to anonymous users by default (grant on purpose). `supabase/tests/31_anon_lockdown.sql` fails when a function becomes anonymously callable without being on its allowlist. The identity review and audit tables carry the RESTRICTIVE "Centre isolation" policy. CI (`.github/workflows/test.yml`) runs type-check, lint of changed files, the build and the whole SQL suite (`npm run test:db`); the browser flows are in `e2e/` and run against a live system with a credentials file kept out of the repository.
- Role helpers (migration 20261030090000): the functions that take a user id first (`has_role`, `has_org_role`, `is_super_admin`, `is_org_staff` and the other `is_*_staff` / `can_*` helpers) live in the `private` schema, which the API does not expose, and policies, defaults and views keep using them there. The `public` function of the same name answers an `anon` or `authenticated` caller only about themselves (anyone else gives false/null) and is closed to anonymous users; database functions, the token approvals and the service role get the real answer. Anything new that decides a person's role must follow this pattern, and `supabase/tests/32_role_enumeration.sql` covers it.
- IT Systems Administrator (migration 20261031090000): the Organization Admin is the centre's IT Systems Administrator, not an academic or finance role. Its dashboard (`it_dashboard`), diagnostics page (`it_system_status`) and navigation cover support tickets, escalations to the Super Admin, user accounts and ordinary roles, centre setup, activity logs and the audit trail; the academic, results and finance pages are closed to it (`blockedRoles` in `withRoleAccess`, plus the database gates above), and its figures come from the database, never from hardcoded values. Support tickets change only through `support_ticket_add_message`, `support_ticket_assign`, `support_ticket_set_status`, `support_ticket_escalate` and, for the Super Admin, `support_ticket_super_action`; messages in `support_ticket_messages` are append-only, internal troubleshooting notes are never shown to the requester, a ticket with the Super Admin cannot be resolved by the centre, and the Super Admin answers escalations at `/escalated-tickets`. A ticket can be assigned only to an Organization Admin of the same centre.
- IT administrator boundaries (migration 20261101090000): the Organization Admin cannot write the academic operational tables (classes, timetable, assessments, trainers and related; restrictive "IT administrators do not change academic records" policies via `not_it_admin()`), and is no longer admitted by `publish_timetable`, `issue_transcript`, `lock_assessment_cycle`, `request_application_info` or `allocate_trainee_identity`. New academic tables need the same three policies. Message delivery needs the Vault secrets `vms_functions_url` and `vms_dispatch_secret`; `message_delivery_configured()` feeds the dashboard and system status so a missing set-up is shown as such rather than as stuck messages.
- Test data reset (migration 20261102090000): test people are identified by `trainee_identities.is_test` (set automatically for `TEST-` numbers, or by the Super Admin through `mark_test_identities`), test staff logins by the `@vms-test.example` domain. `reset_test_data(dry_run, include_staff)` is Super Admin only, previews by default, removes the test identities with every dependent row (followed by `private.purge_cascade`, which turns triggers off for the transaction and refuses to remove core set-up rows such as organizations or qualifications), their logins when those belong to no real person and hold no staff role, and queued messages, and writes counts to the append-only `test_data_purges`. It is the one sanctioned way to delete issued numbers and append-only rows, and only for test records; the page is `/test-data-reset`. New tables that reference users without a foreign key must use a `user_id` column so the sweep finds them. The reset also removes log entries that only name a removed record or login (`entity_id`/`record_id`/`subject_id`/`actor_id` sweeps) and queues files uploaded by test logins in `test_storage_queue` for the `purge-test-storage` edge function (the database cannot delete storage files); `seed-test-accounts` (Super Admin only) recreates one test login per role for a centre and returns the generated passwords once, never storing them.
- Uniform and PPE needs (migration 20261103090000): the sizes applicants enter (shoe, overall, t-shirt, skirt/trousers, chef trousers and jacket on `trainee_applications`) reach the Procurement Officer only for trainees whose registration is `registered` (and not withdrawn or transferred), through `uniform_ppe_needs` / `uniform_ppe_register` (procurement officer, stock control officer and centre manager at that centre) and the "Uniforms & PPE" tab of the procurement dashboard. `create_uniform_requisition` (procurement officer only) turns the outstanding sizes into a draft `purchase_requisitions` row with one line per item and size and zero unit costs; `ppe_requisition_registrations` records each registration once, so a trainee is never requisitioned twice.
- Purchase requisitions (migration 20261104090000, phase 1 of `docs/requisition-and-org-structure-plan.md`): a requisition is a `purchase_requisitions` row driven by the workflow engine's `purchase_requisition` process with four fixed stages (requester's configured line supervisor `@supervisor`, Accountant with Fund available + GL code, Head of Finance and Administration, Centre Manager); the stages cannot be edited (`guard_requisition_steps`), the requester never chooses the supervisor and submission is blocked when none is valid (`requisition_my_supervisor` shows it on the form), and one person never decides two stages of the same requisition (the later stage goes to their own supervisor). Everything goes through `requisition_save_draft` / `requisition_submit` / `requisition_decide` / `requisition_reopen` / `requisition_cancel`; the generic `workflow_act`, `workflow_provide_info` and `workflow_cancel` refuse requisitions, direct table writes are refused, and `status` can only change through `private.requisition_set_status` (guard trigger). Decisions, status history and the content of each submitted round are append-only (`requisition_decisions`, `requisition_status_history`, `requisition_snapshots`); a correction starts a new round and never overwrites an earlier one. Reads go through `requisition_view` / `requisition_list` (requester, people involved, Centre Manager, and the Procurement Officer only after final approval). The printed Internal Quotation Request Form is `requisitionDocumentHtml` in `src/lib/requisitionDocument.ts`, and it uses the same centre letterhead (`src/lib/letterhead.ts`, shared with the proof of registration, whose output must stay byte-identical) with the people and roles taken from the requisition itself. The Procurement Officer's PPE requisitions are drafts in this same process.
- Requisition procurement and receipt (migration 20261105090000, phase 2): after final approval the Procurement Officer records supplier, quotation, the order (reference, date, expected delivery), delays, notes and documents (`requisition_procurement_save`, `requisition_place_order`, `requisition_record_delay`, `requisition_add_note`, `requisition_add_document`); an order never counts as received. Deliveries are recorded by the receiving officer (`stock_control_officer` or `asset_maintenance_coordinator`; the Procurement Officer only at a centre with neither, so ordering and receiving stay with different people) through `requisition_record_receipt` against the individual item rows: accepted quantities count as received, damaged/incorrect/missing quantities open `requisition_discrepancies`, over-receipt beyond the outstanding quantity is refused, partial deliveries are supported and the requisition row is locked so simultaneous deliveries cannot overshoot. Status moves partially_received → fully_received (every item accounted for, counting cancellations made by resolving a discrepancy) → closed only through `requisition_close` (Procurement Officer or Centre Manager, no open discrepancy, closer and date recorded); `requisition_cancel_order` works only before any receipt. Receipts, receipt lines and the procurement log are append-only. `requisition_fulfilment` is the one read for the detail page, `requisition_procurement_summary` feeds the Procurement Officer dashboard.
- Centre Manager dashboard (migration 20261106090000): the dashboard data functions (`centre_manager_overview`, `centre_manager_executive`, `centre_manager_finance`, `centre_manager_quality`, `centre_manager_staffing`, `centre_manager_stakeholders`) admit the Centre Manager and platform staff only, never the Organization Admin (IT administrator). Figures are read from live records: fees are per academic year, budgets from `department_budgets`, NSFAF funding from the `funding_*` tables, spending from the requisition pipeline and the order value the Procurement Officer records (`requisition_set_order_value`), vacancies from `staff_establishment` (kept by the HR officer through `save_staff_establishment`) against the people holding each role, and reports and reviews due from the PA's `office_tasks` of source `report` / `review`. Targets live in `centre_targets` (kept by the PA through `save_centre_target`, read by the Centre Manager) so the Centre Manager stays read-only; a panel shows an empty-state message, never a made-up figure, when the underlying data has not been entered.
- Centre Manager navigation: `centreManagerNavItems` is grouped by the job-description duties (Leadership, Financial Management, Quality of Training, Staff Management, Administration). Pages that belong to other roles are view-only for the Centre Manager in the UI as well as the database: classes (read-only `ClassesTab`, no buildings or rooms), graduation ceremonies and surveys, transcripts (no issuing); trainee, trainer and transfer controls were already role-gated, and deferral requests are not offered because the Centre Manager has no deferral access.
- Requisition template manager (migration 20261107090000, phase 3): `requisition_templates` holds the versioned definition (instructions, renamable labels, extra header `fields`, extra item `columns`, mandatory `documents`); the approval stages and decisions are never part of a template (`private.requisition_validate_template` refuses anything else, and purpose, department, quantity and description are fixed and always required). Version 1 is the built-in form (`private.requisition_default_template`); the Procurement Officer proposes (`requisition_template_save_draft` / `requisition_template_submit` / `requisition_template_withdraw`) and the Head of Finance and Administration (the Centre Manager only at a centre with none) confirms or rejects (`requisition_template_decide`), never the proposer; one open proposal per centre, one published version, submitted versions are immutable and kept, and every step is in the append-only `requisition_template_events`. A requisition is pinned to the template it was created on (`template_id`, `template_version`, values in `custom_fields` and `purchase_requisition_items.extra`; each round's field values are in `requisition_snapshots.fields`); `requisition_submit` enforces the pinned template's required fields, columns and documents, and requester documents go through `requisition_attach_request_document` / `requisition_remove_request_document` (kind `request`). The form (`RequisitionEdit`), detail page and printed form (`requisitionDocumentHtml`) all render from the pinned template; the manager page is `/requisition-template`.
- Class and facility approval (migration 20261108090000): classes, buildings/workshops (`training_buildings`) and rooms (`training_rooms`) are made by the Head of Training and approved by the Centre Manager. Rows that existed stay `approved`; a row made by a signed-in user always starts `pending` (`facility_approval_guard`), the approval columns change only through `facility_decide` (Centre Manager of that centre, rejection needs a reason, a room needs its building approved first, decisions are final), and correcting a rejected item sends it back to pending. Pending or rejected classes cannot be enrolled or timetabled and pending or rejected rooms cannot be timetabled (`facility_use_guard`); automatic enrolment only uses approved classes and approving a class enrols its matching trainees. Every step is in the append-only `facility_approval_events` and the Centre Manager is notified (type `facility_approval`). Test fixtures that insert classes under a signed-in claim set `app.facility_fn` to `on` first. The Centre Manager sees all three tabs read-only with Approve/Reject on pending items (`ApprovalCell`), and the dashboard shows what is waiting (`facility_approval_summary`).
- Reporting structure (migration 20261109090000, phase 4): `reporting_lines` and `user_supervisors` are no longer written directly (the Organisation Admin has no write policy); changes go through `reporting_set_supervisor` / `reporting_remove_supervisor` / `reporting_set_line` / `reporting_remove_line`, which check that the person and supervisor belong to the centre, the supervisor is active, nobody supervises themselves, no loop is created (person-level and role-level), dates are not in the past, and an administrator never makes themselves a supervisor. Named supervisors carry `effective_from` / `effective_to` (a new one ends the earlier one the day before; routing reads `private.reporting_supervisors_at`, and `workflow_supervisors_of` is that function for today). A change to the Accountant, Head of Finance and Administration or Centre Manager (by name or by role line, `private.reporting_protected_roles`) is only a `reporting_change_requests` row until a Super Admin confirms it with `reporting_decide_change` (rules are re-checked then; the Super Admin's own changes apply directly). Waiting approvals move only through `reporting_reassign_pending` (reason required, never to the submitter or to the administrator, one person never decides two stages of a request, logged on `workflow_events` and `reporting_events`); decisions already taken are never touched. `reporting_org_chart`, `reporting_gaps`, `reporting_preview` and `reporting_events_list` feed `/reporting-structure`; the Super Admin confirms at `/reporting-confirmations`.
